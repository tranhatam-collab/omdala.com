## Scope and method

The current filesystem was inventoried before canonical-source recovery. For every readable source candidate, the snapshot records:

- repository-relative path;
- byte size;
- modification epoch;
- SHA-256 digest.

The scan deliberately excluded:

- `.git` data and alternate `.claude/worktrees`;
- dependency/cache/build output such as `node_modules*`, `.next`, `out`, `dist`, `build`, `coverage`, `.pnpm-store`, test and Lighthouse reports;
- secret-bearing environment/key/credential candidates.

Secret candidates were classified by path only. Their contents were not opened or hashed. Example/sample/template environment files were treated conservatively when their names matched the secret filter.

## Coverage gap

Exactly 290 candidate files were marked `DATALESS_NOT_HASHED`. macOS reports these files with the `dataless` flag; hashing them would require hydration and could alter local/cloud filesystem state. They are therefore recorded by path in `read-failures.log` and intentionally deferred to G0.3.

G0.2 is complete as a truthful partial-content snapshot:

- 1,169 readable files are content-addressed;
- 290 unavailable files are explicitly identified;
- 7 secret candidates are excluded by path;
- 115 generated/dependency directories are excluded by path.

It is **not** valid to describe the complete filesystem as fully checksummed until G0.3 hydrates the 290 dataless files and a second manifest closes the gap.
