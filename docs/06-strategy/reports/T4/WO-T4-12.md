## Conclusion
- `apps/app`: a staging build made before `5190ac8` sent its session check to the production API. A staging deployment from such a build would have mixed staging pages with production sessions. Fixed at `5190ac8`.
- `apps/auth`: the same fragile pattern existed (`process?.env?.`), but the compiled bundle happened to inline the staging value on the request path I exercised, so no misrouting was observed. The fix is still right (removes the dependence).
- Proposed for T1: confirm which commit every deployed staging `app` artifact was built from (the staging go-live specs assert the exact SHA; an origin assertion on the built bundle, as in this report, would catch a regression) and add the bundle-origin check to the surface artifact verifier. Add the same grep to CI for all surfaces that read `NEXT_PUBLIC_API_URL`.
