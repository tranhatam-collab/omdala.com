## Findings (T2; WO-T2-29 is the right order and is still READY)
1. Medium, `index.ts:3935`: an unauthenticated route in production that performs HMAC work with caller-supplied secrets. It is not an oracle for OMDALA secrets (the secret is the caller's), but it is unauthenticated, unrate-limited compute and a pattern that invites misuse. Close with 501 in release environments, as ordered.
2. Low, `index.ts:3958`: service-token minting falls back to `MAGIC_LINK_SECRET`, the session-signing key. I checked for cross-use: the service token signs `{"sub":…}` JSON text, session tokens sign a base64url string, so a minted token's signature cannot be replayed as a session signature (the message alphabets cannot overlap). Still key reuse without domain separation; the order to close the route removes it, and a future design should use its own secret.
3. Low, same four handlers (`index.ts:3914-3994`): 500 responses echo `error.message`; WO-T2-28 (error hygiene) is the order for that.
4. No other route accepts a secret from the caller: grep of request bodies for secret, apiKey, password, token fields finds only the two security verify routes and the magic-link token exchange (a single-use token, not a secret).
