Findings (T2 owns `services/api/scripts/**`)
1. Low/Medium, `local-stack.mjs:41-45`, called at `:154`, `:163`, `:230`: `fail()` calls `process.exit(1)` directly and skips `teardown()`. When the worker never becomes healthy (timeout at `:163`) or the scratch connection fails after the scratch database was created, the scratch database, the TLS proxy's work directory (holding the 0600 secrets file) and, in the timeout case, the still-running wrangler child are left behind. Fix: make `fail` async-teardown first (or throw into the `main().catch` path that already tears down).
2. Low, `:108-109`: only SIGINT and SIGTERM run teardown; SIGHUP and a hard kill leave the same leftovers. Acceptable for a dev script if documented.
3. Low/Medium: the worker inherits the top-level `[vars]` of `services/api/wrangler.toml` (`MAIL_DELIVERY_MODE="direct"`, `MAIL_API_URL` pointing at the real mail host). The smoke only sends to the console transport because no `MAIL_API_KEY` is present. A developer's untracked `services/api/.dev.vars` containing a mail key would be read by `wrangler dev`, and the smoke would send real mail before its assertion at `:177-185` fails. `.dev.vars` is not matched by `.gitignore` in this repo (checked with `git check-ignore`). Fix: pass `--var MAIL_DELIVERY_MODE:console` (or blank the key) explicitly and add `.dev.vars` to `.gitignore` (T1 owns the root file). Not reproduced; reasoning only.
4. Info, `:222-224`: the admin and scratch connections retry with `rejectUnauthorized: false`; acceptable because the host is already restricted to loopback, but worth a comment.

Workerd TLS finding ("workerd ignores `rejectUnauthorized: false`")
- Minimal reproduction attempted in an untracked temp worker (deleted afterwards, repo untouched): `wrangler dev --local` with `nodejs_compat`, a `pg` client to the container's TLS-enabled PostgreSQL 16 (self-signed "snakeoil" certificate), once with `ssl: { rejectUnauthorized: false }` and once with `true`. Result: BOTH modes failed identically with "Connection terminated unexpectedly", so `false` did not make the connection succeed. That is consistent with T2's claim.
- Not isolated: trusting that certificate through `SSL_CERT_FILE` also failed (the snakeoil certificate probably lacks a usable SAN for 127.0.0.1), and the failure text did not name the TLS reason, so I cannot confirm T2's exact error string. The positive control that does work is T2's own CA-plus-proxy design, which `local:smoke` exercised (exit 0).
- Proposed next order for T2: add a one-line comment with the exact workerd error text and the wrangler version (4.114.0 here) next to the CA workaround, and a negative-control mode (`--no-ca`) in the script so the claim can be rechecked in one command.
