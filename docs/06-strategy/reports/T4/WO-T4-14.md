Status: DONE with one **HIGH** finding (cap bypass). Evidence: VERIFIED_HEAD_ONLY (real PostgreSQL 16 scratch database, real handlers and SQL; provider stubbed in-process; temporary test files deleted, tree clean).

## 1. Cost cap: bypass through replay of a released Idempotency-Key  (HIGH, reproduced)
- Where: `services/api/src/index.ts:4057-4105` (`reserveChatBudget`) with `services/api/src/db/ai-usage-repository.ts` (`reserveAiUsage`, duplicate branch).
- Mechanism: the ledger row is keyed by (account, request id) where the request id derives from the `Idempotency-Key`. When a row already exists, `reserveAiUsage` returns `duplicate` (any status) and `reserveChatBudget` returns `null` for it (`return reserved.outcome === "reserved" ? {...} : null`, 4103), meaning "no reservation, go on". The route then calls the provider (`index.ts:4170-4180`). That is right for a key that was `reserved` or `settled` (the provider deduplicates by request id), but wrong for a key whose reservation was `released`: release means "nothing was dispatched", so the provider has never seen that id, and the replay executes with no reservation and no settlement.
- Reproduction (staging-shaped environment, cap 1.00 USD, each provider call reports 0.40 USD, session cookie of one account): (1) five requests with distinct keys naming a model the provider does not list: all answered 422 `invalid_ai_request` and the five ledger rows ended `released`; provider executions 0. (2) honest requests on new keys until the cap stopped them: counter reached 1.000000 and further new keys answered 429 `ai_tenant_cap_exceeded`. (3) the same five keys replayed with a listed model while the cap was exhausted: the provider executed **5 more calls**, the counter stayed at 1.000000, the five rows stayed `released`. Control in the same state: a brand-new key answered 429. (My stub's receipts were incomplete, so the replays returned 502 to the caller; the provider had already executed.)
- Impact: the per-account daily cap can be exceeded without bound. The attacker stages released keys while budget remains (each staging request is a cheap refusal that never reaches the provider), then replays them after the cap is exhausted; the rows persist across days, so a key staged once is reusable later. Limits that still apply: the 20 requests per minute per account limiter, the per-call 0.25 USD provider ceiling, and the provider's own quota.
- Fix owner T2. Proposed: in the `duplicate` branch, treat status `released` as "not reserved": re-reserve it atomically (flip the same row back to `reserved` only if the cap allows, in one conditional statement) or refuse the replay with a new key required; and return `null` only for `reserved`/`settled`. Add a real-SQL test with this exact sequence (it must fail today). Also validate the model/input before reserving (T2's WO-T2-22 commit title says it now validates chat input before reserving; that narrows how a key gets released but does not remove the replay path for other release causes such as a provider refusal before dispatch).

## 2. Cost cap: other checks
- Parallel reservations: the 583-test run includes T2's real-SQL concurrency tests (40 parallel reserves at cap 1 admit exactly 4; replays admit 1); they passed here. The reservation statement is a single conditional UPDATE on the day counter, which serializes writers. I did not find an over-admission path through distinct keys.
- Fail closed: cap unset or invalid outside local/development/test answers 503 `ai_cap_not_configured`; cancelled or past-due plan answers 402 before reserving (`index.ts:4072-4080`).
- Known by design (T2 documents): a failure to close the ledger after the answer is logged only; an unclosed reservation counts until the UTC day ends.
